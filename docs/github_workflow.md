# GitHub運用ルール

## 1. 用語定義

- `master`（または `main`）:
  - 既定の統合先ブランチ（GitHub上のデフォルトブランチ）。常に統合可能な状態を維持する。
- `作業ブランチ`:
  - 1つの機能追加または不具合修正を実装するための短命ブランチ。
- `PR (Pull Request)`:
  - ブランチ変更のレビューと統合申請。通常PRとDraft PRの総称。
- `通常PR（Ready for review PR）`:
  - レビュー完了後、すぐにマージしても問題ない状態のPR。
- `Draft PR`:
  - まだマージできない状態のPR。作成者がレビューを希望する場合は、レビュー担当者へ直接メンションする。

## 2. 基本方針

- 1ブランチ1トピック（1機能追加 or 1修正）を原則とする。
- 作業完了後は `master` 向けにPRを作成する（原則、直接 `master` へpushしない）。
- 作業ブランチには定期的に `master` の最新変更を取り込む（`merge` ）。
    - 個人作業中で未共有の作業ブランチに限り、PR作成前の履歴整理目的で `rebase` を許可する。
- PR作成前やマージ前には `master` が最新であることを確認し、作業ブランチを最新の `master` にrebaseする。
- 長期間放置される枝分かれブランチを作らない。
- `master` は常にビルド・動作確認可能な状態を維持する。

## 3. 通常開発フロー（基本）

1. `master` から作業ブランチを作成する。
2. 実装・コミットする。
3. 必要に応じて `master` の更新を取り込む。
4. `master` 向けPRを作成し、レビュー後にマージする。

## 4. Commit運用ルール

- コミットは「動作確認できた論理的最小単位」で行う。
- 壊れている状態のコミットは原則作らない（必要な場合は `WIP` を明示）。
- AIによる変更は、意味的にまとまる単位で整理してコミットする。
- 自動生成物やフォーマット変更など機械的変更は、本質的変更と可能な限り分離する。

コミットメッセージ形式:

- `type: summary`

`type` 一覧:

- `feat`: 機能追加（新規ファイル追加を含む）
- `fix`: 不具合修正
- `docs`: ドキュメント修正
- `refactor`: 挙動を変えない構造改善
- `test`: テスト追加・修正
- `chore`: 雑多な保守作業（設定、依存更新など）

例:

- `feat: add record and replay CLI options`
- `fix: correct generated URL in replay output`
- `docs: update github workflow rules`

## 5. PR運用ルール

- 1機能（1目的）につき1PRを原則とする。
- PRは作成から1〜2日以内のマージを目標にする。
- PRタイトルは内容が一読で分かる形式にする。
- 推奨タイトル形式: `type: summary`

### 5.1 PRの状態とレビュー

- 通常PRは、レビュー完了後にすぐマージしても問題ない状態で作成する。
- 通常PRは担当者が速やかにレビューする。
- Draft PRは、マージ可能な状態になるまでDraftのままにする。
- Draft PRをレビューしてほしい場合、作成者はレビュー担当者へ直接メンションする。メンションされたDraft PRのみ、担当者がレビューする。
- Draft PRがマージ可能な状態になったら、作成者が通常PRへ変更する。

PR本文に書く項目の例:

- やったこと（変更内容）
- 確認したこと（テスト/実機確認）
- 懸念点（未解決事項、リスク）

実機確認を実施したPRでは、上記に加えて以下も推奨:

- 実機で実行したコマンド（実行順）
- 実機での結果要約（期待動作/実際の動作/差分）
- 必要に応じてログ、スクリーンショット、動画へのリンク

`master` への直接pushについて:

- 少人数開発でも、方針変更・機能追加・不具合修正はPR経由を原則とする。
- 直接pushを許容するのは、誤字修正など方針・挙動に影響しない軽微変更に限定する。

## 6. 試行錯誤ブランチからの統合

実機運用、訓練、実験などでは、試行錯誤のためのブランチを必要に応じて作成してよい。これらのブランチは、常にそのまま `master` へマージできる状態である必要はない。

試行錯誤の結果を `master` へ反映する場合は、AIに統合したい目的を伝え、対象ブランチやDraft PRの差分から必要な変更を選別してもらう。既存のDraft PRを整理して通常PRへ変更する、新しい統合用ブランチから通常PRを作成するなど、統合方法は変更内容に応じて柔軟に選択してよい。`cherry-pick`、部分的な移植、再実装など、変更の取り込み方も特定の方法に限定しない。

統合用PRは1つの目的に絞り、試行錯誤の履歴や不要な変更を無理に含めない。PR本文には、確認しやすい範囲で以下を記載する。

- 変更の取得元となったブランチ
- `master` へ取り込む内容
- 主な確認内容（自動テスト、実機確認、訓練結果など）
- 必要に応じて、意図的に取り込まなかった主な変更

試行錯誤中のブランチにDraft PRを作成するかどうかは任意とし、差分の共有や相談が必要な場合に利用する。`master` へのマージ後も継続して使うブランチは、必要に応じて `master` の変更を取り込む。使い捨てのブランチに再同期は求めない。

## 7. ブランチ命名規則

形式:

- `<type>/<scope>-<short-description>`

`type` 一覧:

- `feat`: 機能追加
- `fix`: 不具合修正
- `refactor`: リファクタリング（挙動変更なし）
- `docs`: ドキュメント修正
- `test`: テスト追加・修正
- `train`: Google Colab などで実行する学習用ブランチ
- `ops`: 実機運用中の長寿命ブランチ
- `integrate`: `master` 統合用ブランチ

例外:

- `train` ブランチは、Google Colab の仕様上 `/` を含むブランチ名が扱いづらい場合があるため、`train-<scope>-<short-description>` のようにハイフン区切りを使ってよい。

命名例:

- `feat/record-cli-args`
- `fix/replay-timestamp-bug`
- `train-cleank2-dp-small-unet`
- `ops/cleank2-live`
- `integrate/cleank2-live-to-master`

## 8. Issue運用（現時点では任意）

- Issueは、課題・背景・完了条件を整理して残すための機能。
- 現時点では、Issueの利用を必須にはしない。
- ただし、変更規模が大きい作業、実機確認が必要な作業、複数人で追う作業では、Issueを使うと管理しやすい。
- 今後の運用状況を見ながら、Issueをより積極的に使う方針へ移行する可能性がある。

Issueを作る場合の最小項目（推奨）:

- 背景（なぜやるか）
- 目的または完了条件（何をもって完了とするか）
- 関連PR（あればリンク）
